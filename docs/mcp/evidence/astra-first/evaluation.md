The Ori Studio MCP supported an autonomous design → inspect → repair → verify → export loop for an editable, asymmetric bird-derived flat-fold design. The final geometry passes the exposed local checks, has one solved layer ordering, and survives FOLD export/import exactly. It did **not** establish the intended substantially folded 3D pose: simulation outputs conflict with the advertised fold-amount convention. A successful simulation job and low strain would have been misleading acceptance criteria on their own.

I chose “Split-wing bird — asymmetric petal base”: a bird-base construction extended with a folded-over corner tip. This is a nontrivial base variant, not a finished representational bird or a demonstrated physical folding sequence. It uses a square sheet, 18 vertices, 37 edges (10 boundary, 10 mountain, 17 valley), and 20 flat-fold faces. Its asymmetric tip adds four creases and reverses the assignments on the three original creases inside that tip. No Miura design was used.

The primary experiment is `009c00ce-2f17-42e6-9cf0-0bb537c22a0c`, final revision **5**. The FOLD round-trip experiment is `200544eb-53cd-4fdb-974c-a8bd6f16a034`, revision **0**. Both remain in the app. `commit_design`, request `bird-publish-final`, published the primary design; subsequent `workspace` independently reported 37 live line segments, the correct title, edit revision 1, and the undo label “Create split-wing bird with folded-over tip.” The application remains running and dirty; the exported OSF is the saved editable deliverable.

All origami/application actions used connected `mcp__ori_studio__*` tools. Discovery used their public catalog and `workspace`. I did not read repository source, implementation documentation, clients, or prior artifacts, and made no implementation/configuration changes. Filesystem use was confined to saving returned content, calculating artifact statistics, and writing this evaluation. No other agent, browser, login, dependency installation, Git operation, or web research was used.

The strongest observed interface problem is simulation target semantics. The catalog says fold_amount is 0..1. The 0.85 job (`8efde957-f9c6-48e3-a938-16faec39f05c`) echoed 0.85 and reported converged=true at step 4304, max_velocity≈9.855e-6 and max_strain≈2.181e-5. The 1 job (`5855c748-aa4b-4667-873f-98083cf77f75`) echoed 1 and converged at step 4528, max_velocity≈9.875e-6 and max_strain≈3.022e-5. Both identified backend=`reference` and returned no warnings or errors. Yet both OBJ headers labeled the geometry 1%. At target 1, the exported vertex extents were x=[-0.707110,0.707086], y=[-0.005709,0.007070], z=[-0.707086,0.707110]: displacement perpendicular to the paper was under 1% of its planar width. This corroborates the images. A fraction/percentage mismatch is a strong hypothesis, **not an implementation diagnosis**. The public interface did not let me determine whether target conversion, backend behavior, export metadata, or more than one layer was responsible. It did reject 85 with `data/fold_amount must be <= 1`, so a percentage workaround was unavailable.

The tool set was otherwise discoverable and useful. The repeated workflow hint made the overall sequence clear. `workspace` exposed units, isolation, limits and construction hints. Separate experiments, revision-scoped IDs, checkpoints and explicit publication made exploration practical. Local checks named Maekawa/NumberOfFolds and gave affected coordinates. Flat-fold jobs exposed solved wireframes, layer information, contradictions and search outcomes, allowing stronger verification than a Boolean success flag. Exports returned actual content and the FOLD round-trip worked exactly.

Concrete interface improvements, in priority order:

1. **P0 — Resolve and expose simulation target units and attainment.** Backed by `bird-sim-05`, `bird-sim-full-05`, the 85 rejection and both OBJ results above. Return requested fraction, effective backend target, target crease angles, achieved angle residuals and an explicit “settled but target not attained” outcome. A small velocity/strain value does not establish fold attainment. Clarify what backend=`reference` promises relative to the tool description's “real Origami Simulator physics.” Include a simulation job ID and target in the export metadata. This is the principal obstacle to closing the 3D verification loop.

2. **P1 — Make topology normalization and repair guarantees explicit.** `bird-geometry-01` accepted overlaps and unsplit crossings; this was my authored input, not an allegation that adding overlapping segments is inherently erroneous. However, `bird-repair-overlaps` made no reported line change and overlaps persisted. `bird-repair-intersections` left two junction issues after one call. Provide a documented normalize operation or a repair result listing resolved, remaining and unsupported issues. Distinguish geometry changes from revision/selection changes: changed=true, revision increment, and “Changed 0 line(s)” were semantically ambiguous. I recovered through explicit geometry replacement, not through a complete built-in repair workflow.

3. **P1 — Improve actionable diagnostic references and deduplication.** `checks1` and `checks3` repeated many zero-length marker segments for the same vertices and exposed internal colors such as Black0/Blue2. Diagnostics supplied coordinates but not the revision-scoped crease IDs needed by edit_creases. Return grouped vertex/edge issues, implicated line IDs, vertex degree and M/V counts, sector angles for angular failures, and suggested repair scope. Prioritize topology errors before downstream flat-foldability noise. This would reduce output volume and manual coordinate matching.

4. **P1 — Preserve complete schemas in discovery.** In the catalog delivered to this client, edit_tree operations appeared as `Array<unknown | unknown | ...>` despite the description promising typed operations. I did not exercise TreeMaker and cannot say whether another client receives a richer schema. The displayed analyze_design signature also omitted case_limit bounds; the <=16 rule emerged only through rejection. Supply tagged union variants and all numeric bounds in the agent-visible declaration and/or a dedicated capabilities/schema response. Export-kind and import-format support matrices would make choices clearer; OSF export is advertised, but OSF import is absent from begin_design.

5. **P2 — Define construction anchors without assuming GUI knowledge.** `workspace.construction_inputs.bases` says “matching the Oriedita template markers,” which a fresh external client cannot see. My initial bird_base preview extended outside the default sheet with diagnostics=[]. Give ordered geometric meanings, canonical anchor coordinates and an optional placement footprint/out-of-sheet warning. Preview itself was a successful recovery mechanism and prevented an unwanted mutation.

6. **P2 — Offer bounded waiting and richer job receipts.** Short checks/solves completed in tens of milliseconds but still required start and poll calls. `bird-checkpoint-03` was rejected with draft_busy while its check job ran; the rejection helpfully named the exact job. After polling, `bird-checkpoint-03b` succeeded. Support wait_ms or optional terminal results on start, explain which read/checkpoint/export operations are blocked, and return revision/line-ID deltas after edits to avoid a mandatory inspection round trip. The busy refusal was understandable synchronization behavior, not data loss.

7. **P2 — Improve rendered feedback provenance and controls.** Render metadata returned draft, revision and view, but not the requested camera, effective projection, originating job ID, target or attained fold. Folded images hid most internal layers and the apparent left/right orientation changed after the tip edit; starting-face dependence is a plausible explanation, not a proven renderer defect. Add stable orientation controls, layer/wireframe/crease-ID overlays, diagnostic overlays and explicit camera transforms. A layer-inspection view would make a solved but visually opaque result easier to assess.

8. **P2 — Reduce redundant payloads and support artifact resources.** Results duplicated large JSON in text and structuredContent, especially repeated diagnostic segments and flat-fold wireframes. Optional summaries/pagination, geometry handles, binary resource links and content hashes would reduce transport and persistence work. Locally, saving the combined evidence JSON in one shell invocation exceeded the process argument limit; I recovered by chunking my own returned evidence. That was an evidence-client limitation, not an Ori MCP failure. No application artifact was reconstructed or changed.

Failure/recovery coverage was naturally occurring, not an exhaustive conformance test. Observed recoveries included construction preview correction, incomplete repair fallback, draft_busy polling, a case_limit validation error, simulation-unit investigation, and an exact editable round-trip. I did not test cancellation, rollback execution, stale-revision conflicts, lost-response/idempotency recovery, optimizer failures, TreeMaker/BP workflows, or restart persistence. Their advertised existence should not be mistaken for verified behavior. The workspace also returned excluded_issues=[366,367,368] without explanatory text; I did not look those issues up, and cannot associate them with any observation here.

Result quality is satisfactory as an editable, locally valid, globally layer-solved asymmetric origami base. The final loop was genuinely closed for that scope through structured diagnosis, geometry/assignment repair, visual inspection and export/import verification. It remains incomplete for a substantially folded physical 3D pose or a collision-free folding motion. Those limits follow from observed outputs, not from stopping at a successful tool call.
